# 03 · i18n 아키텍처 — 여섯 로캘, 하나의 코드베이스, 크롤러를 속이지 않음

[English](../en/03-i18n.md) · [简体中文](../zh/03-i18n.md) · [日本語](../ja/03-i18n.md) · `한국어` · [Deutsch](../de/03-i18n.md) · [Italiano](../it/03-i18n.md) · [Español](../es/03-i18n.md)

시작하기 전에 가장 읽었더라면 좋았을 문서입니다. 여기 있는 것 중 특별한 기법은 하나도 없고, 전부 느리게 배운 것들입니다.

## 하나의 코드베이스, 배포별 로캘 스코프

같은 빌드가 네 가지 **로캘 스코프**를 지원하며, 환경 플래그 하나로 빌드 시점에 고정됩니다:

| 스코프 | 생성되는 라우트 | 사용처 |
|---|---|---|
| `en` | 영어만 | 비공개/프리뷰 빌드 |
| `zh` | 简体中文만 | roomake.cn |
| `both` | EN + `/zh` | 과도기 |
| `global` | EN(루트) + `/ja` `/de` `/fr` `/ko` | roomake.top |

이를 안전하게 만드는 메커니즘: `[locale]` 세그먼트의 `generateStaticParams`가 해당 스코프의 로캘 목록을 반환하고(zh 전용 빌드는 빈 목록), `dynamicParams = false`가 목록 밖의 로캘 요청이 렌더링된 소프트 404 페이지가 아니라 **빌드 시점의 하드 404**가 되도록 보장합니다. 빌드되지 않은 로캘은 출력물에 문자 그대로 존재하지 않으므로, 크롤러가 절반쯤 번역된 로캘을 발견할 일은 없습니다.

URL 구조는 단순한 하위 디렉터리입니다. 영어는 루트에, 나머지 모든 로캘은 `/{locale}/` 아래에 둡니다. 로캘 서브도메인도, 쿼리 파라미터도, 쿠키 기반 협상도 없습니다(그 이유는 SEO 섹션에서 다룹니다).

## 올바른 `lang`을 위한 멀티 루트 레이아웃

Next.js 16은 라우트 그룹을 통해 여러 루트 레이아웃을 허용하며, 이것이 `<html lang>`을 정직하게 유지하는 가장 깔끔한 방법입니다. `(main)` 그룹이 영어 트리를 담당하고, `(i18n)/[locale]` 그룹이 현지화된 트리를 담당하며, 각 루트 레이아웃이 자신의 `lang`을 새겨 넣습니다. `lang` 속성을 클라이언트 측에서 수습하지 않습니다 — 크롤러와 번역 도구는 서버 HTML을 읽습니다.

시간을 잃게 만든 Next 16 특이 사항 두 가지:

- **`params`는 Promise입니다.** 다이내믹 레이아웃/페이지는 `params`를 `await`하는 `async` 컴포넌트여야 합니다. TypeScript 빌드가 잡아 주지만, 맡겨 두어야만 잡아 줍니다.
- **진짜 전역 404에는 `experimental.globalNotFound`가 필요합니다.** 루트 레이아웃이 여러 개면 매칭되지 않는 최상위 URL이 일반 `not-found.tsx`를 우회합니다. 전역 404 파일은 자체 `<html>`/`<body>`를 가져야 하고 **스코프를 인지**해야 하며, 그래야 zh 전용 배포의 404 페이지가 그동안과 바이트 단위로 동일하게 유지됩니다. 공유 빌드 플래그의 영향 반경은 전역입니다 — 모든 스코프를 테스트하세요.

## 프레임워크 없는 사전

번역은 기능 영역별로 정리된, 타입이 붙은 일반 TypeScript 사전이며 **문법이 요구하는 곳에는 함수 필드**를 둡니다 — 독일어의 복수형, 일본어/한국어의 카운터(수량 표현)는 문자열 보간이 아니라 함수로 표현됩니다. 영어 사전이 형태의 기준이고, 나머지 모든 로캘은 같은 타입을 채워야 합니다.

리팩터링을 안전하게 만드는 규율은 **골든 마스터 diff**입니다. 영어 문자열을 사전 시스템으로 추출할 때 합격 기준은 핵심 페이지의 렌더링된 HTML이 *바이트 단위로 동일*하게 유지되는 것이었습니다. "시각적 회귀가 없다"는 의견이고, 비어 있는 diff는 사실입니다.

## 번역하는 것과 하지 않는 것

- **브랜드 어휘는 모든 곳에서 영어로 유지합니다**: 스타일 이름(Cream, Wabi Sabi…), 요금제 이름, 제품 이름. 시적인 부제목은 번역하고, 고유명사는 번역하지 않습니다.
- **법적 고지 페이지는 영어 버전이 효력의 기준**이며 현지화된 안내 문구를 곁들이되, 법이 실제 현지화 고지를 요구하는 경우만 *예외*입니다(아래 참고).
- **나머지는 전부 현지화합니다.** 이미지 `alt` 텍스트까지 포함입니다 — Google Images는 인테리어 디자인의 중요한 발견 채널이고, alt 텍스트는 그 현관문입니다.

## 실제로 마주친 언어별 함정

- **일본어**: クレジット(credit)는 クレジットカード(신용카드)와 충돌합니다 — 처음 쓰는 지점에서 구분해 주세요. 문장부호 규칙을 위해 `line-break: strict`를 추가합니다. 가타카나로 음역된 스타일 이름은 아티클에는 어울리지만 UI에는 절대 쓰지 않습니다.
- **한국어**: 자체 세리프 서체(아래 참고)와 고유의 카운터가 필요합니다. 기계 번역된 마케팅 한국어는 눈에 바로 드러나므로 사람의 검수는 타협 불가능한 항목입니다.
- **독일어**: +30% 텍스트 팽창이 고정 폭 레이아웃을 깨뜨립니다 — 긴 합성어(`Renovierungsvorschau`)는 출시 후가 아니라 출시 전에, 좁은 폭에서 테스트하세요.
- **프랑스어**: 사전 스타일 가이드에 따라 곧은 따옴표가 아니라 길러메 « »를 사용합니다.
- **날짜**: 항상 `Intl.DateTimeFormat(locale)` — 손으로 조합한 미국식 날짜 형식은 쓰지 않습니다.
- **숫자/통화**: 모든 로캘에서 USD를 유지합니다 — 가격 브랜드에 관한 결정이며, 일관되게 적용합니다.

## 폰트: 세리프 아이덴티티와 CJK 현실

아이덴티티 폰트(Fraunces, Newsreader)는 빌드 시점에 `next/font`로 셀프 호스팅합니다. 일본어와 한국어에는 Noto Serif JP/KR을 CSS 변수를 통해 일치하는 `html[lang]` 아래에서 *만* 주입합니다 — 다른 로캘의 페이지는 CJK 글리프를 내려받지 않습니다.

눈에 띄지 않는 세부 사항 하나: Next 16에서 JP/KR 폰트 타입에는 `japanese`/`korean` 서브셋이 **포함되지 않습니다** — CJK 글리프 슬라이싱은 `unicode-range`를 통해 자동으로 일어납니다. `subsets`를 넘기면 타입 에러이고, 서브셋 없이 `preload: false`를 넘기는 것이 올바른 형태입니다. 모든 것을 설정하고 싶은 본능보다 메커니즘을 신뢰하세요.

## 현지화된 법적 고지, 항목별로

현지화된 제품 화면은 현지화된 법적 의무를 만듭니다. 우리가 다루는 항목:

- **일본**: 실제 特定商取引法に基づく表記(일본의 특정상거래법 표기 — 판매자명, 책임자, 주소, 전화번호, 이메일, 결제 수단, 서비스 제공 시점, 환불 정책). 해외 사업자를 위한 소비자청 가이드는 필수 기재 항목을 명확히 요구합니다.
- **독일**: Impressum 수준의 사업자 식별 정보(DDG §5).
- **프랑스**: LCEN 발행 책임자 식별 정보.
- **프라이버시 추가 조항**: 일본용 APPI 국외 이전 문구, 한국용 PIPA 고지, EU용 GDPR 요소(적법한 처리 근거, 동의 철회, 국외 이전에 관한 진술) — 결제 데이터를 merchant of record가 처리하는 서비스에 걸맞은 비례의 수준으로.
- **번역하지 않고 항상 링크**: 효력의 기준이 되는 영어 약관/프라이버시/환불 페이지를 모든 로캘의 푸터에 링크합니다.

## 롤백: 색인된 URL은 절대 404로 만들지 않는다

잘못된 순서로 로캘을 제거하면 그 URL들이 쌓아 올린 검색 자산이 증발합니다. 순서는 고정되어 있습니다:

1. 폐지하는 로캘에서 대체 페이지(보통 영어 페이지)로 향하는 프록시 수준의 301 리디렉션을 설치합니다.
2. 그 후에야 라우트를 제거하고 다시 빌드합니다.

같은 패턴이 모든 구조 변경에 적용됩니다: 리디렉션이 먼저, 삭제는 나중. GSC는 301을 조용히 흡수하지만, 404에는 크게 소리칩니다.
