# 03 · i18n architecture — six locales, one codebase, no lies to crawlers

`en` · [简体中文](../zh/03-i18n.md) · [日本語](../ja/03-i18n.md) · [한국어](../ko/03-i18n.md) · [Deutsch](../de/03-i18n.md) · [Italiano](../it/03-i18n.md) · [Español](../es/03-i18n.md)

This is the document we most wish we had read before starting. Nothing here is exotic; all of it was learned the slow way.

## One codebase, per-deployment locale scopes

The same build supports four **locale scopes**, fixed at build time by one environment flag:

| Scope | Routes generated | Used by |
|---|---|---|
| `en` | English only | private/preview builds |
| `zh` | 简体中文 only | www.roomake.cn |
| `both` | EN + `/zh` | transitional |
| `global` | EN (root) + `/ja` `/de` `/fr` `/ko` | roomake.top |

The mechanism that makes this safe: the `[locale]` segment's `generateStaticParams` returns the scope's locale list — an empty list for zh-only builds — and `dynamicParams = false` ensures a requested locale outside the list is a **hard 404 at build time**, not a rendered soft-404 page. A crawler can never discover a half-translated locale, because unbuilt locales literally do not exist in the output.

URL structure is plain subdirectories: English at the root, every other locale under `/{locale}/`. No locale subdomains, no query parameters, no cookie-based negotiation (more on why under SEO).

## Multi-root layouts for correct `lang`

Next.js 16 allows multiple root layouts via route groups, and that is the cleanest way to keep `<html lang>` honest: a `(main)` group holds the English tree, an `(i18n)/[locale]` group holds the localized trees, and each root layout stamps its own `lang`. No client-side patching of the `lang` attribute — crawlers and translation tools read the server HTML.

Two Next 16 specifics that cost us time:

- **`params` is a Promise.** Dynamic layouts/pages must be `async` components that `await params`. The TypeScript build catches it, but only if you let it.
- **A true global 404 needs `experimental.globalNotFound`.** With multiple root layouts, unmatched top-level URLs bypass the regular `not-found.tsx`. The global 404 file must carry its own `<html>`/`<body>` and be **scope-aware**, so the zh-only deployment's 404 page stays byte-identical to what it has always been. Shared build flags have global blast radius — test every scope.

## Dictionaries without a framework

Translation is plain typed TypeScript dictionaries, organized per feature area, with **function fields where grammar demands it** — plural forms for German, counters for Japanese/Korean are expressed as functions, not string interpolation. The English dictionary is the shape source; every other locale must fill the same type.

The discipline that makes refactors safe: **golden-master diffs**. When English strings were extracted into the dictionary system, the acceptance criterion was that rendered HTML for core pages stayed *byte-identical*. "No visual regressions" is an opinion; an empty diff is a fact.

## What we translate and what we don't

- **Brand vocabulary stays English everywhere**: style names (Cream, Wabi Sabi…), plan names, the product name. Poetic sublabels translate; proper nouns don't.
- **Legal pages stay English-authoritative** with a localized pointer line, *except* where law demands a real localized disclosure (below).
- **Localized everything else**, including image `alt` text — Google Images is a serious discovery channel for interior design, and alt text is its front door.

## Language-specific traps we hit

- **Japanese**: クレジット (credit) collides with クレジットカード (credit card) — disambiguate on first use. Add `line-break: strict` for punctuation rules. Style names transliterated into katakana belong in articles, never in the UI.
- **Korean**: needs its own serif face (below) and native counters; machine-translated marketing Korean is detectable on sight, so human review is non-negotiable.
- **German**: +30% text expansion breaks fixed-width layouts — test long compounds (`Renovierungsvorschau`) at narrow widths before, not after, launch.
- **French**: guillemets « » , not straight quotes, per the dictionary style guide.
- **Dates**: always `Intl.DateTimeFormat(locale)` — never hand-formatted US dates.
- **Numbers/currency**: kept in USD across locales — a pricing-brand decision, applied consistently.

## Fonts: serif identity with CJK reality

The identity fonts (Fraunces, Newsreader) are self-hosted at build time via `next/font`. Japanese and Korean get Noto Serif JP/KR injected *only* under the matching `html[lang]` through a CSS variable — pages in other locales never download CJK glyphs.

One non-obvious detail: in Next 16, the JP/KR font types do **not** include `japanese`/`korean` subsets — CJK glyph slicing happens automatically via `unicode-range`. Passing `subsets` is a type error and passing `preload: false` with no subsets is the correct form. Trust the mechanism over the instinct to configure everything.

## Legal localization, category by category

Localized product surfaces create localized legal duties. The categories we handle:

- **Japan**: a real 特定商取引法に基づく表記 (seller name, responsible person, address, phone, email, payment methods, service timing, refund policy) — the consumer-agency guidance for overseas operators is explicit about required fields.
- **Germany**: Impressum-level operator identification (DDG §5).
- **France**: LCEN publication-director identification.
- **Privacy addenda**: APPI cross-border language for Japan, PIPA notice for Korea, GDPR elements (lawful basis, withdrawal of consent, cross-border transfer statement) for the EU — proportionate to a service whose payment data is handled by a merchant of record.
- **Not translated, always linked**: the authoritative English terms/privacy/refund pages, from every locale's footer.

## Rollback: never 404 an indexed URL

Removing a locale in the wrong order vaporizes whatever search equity those URLs earned. The order is fixed:

1. Install proxy-level 301 redirects from the retiring locale to its replacement (usually the English page).
2. Only then remove the routes and rebuild.

The same pattern applies to any restructure: redirects first, deletions second. GSC absorbs 301s quietly; it screams about 404s.
