# 05 · デプロイメント — Docker、スコープフラグ、キャッシュ、ロールバック

## 2つのデプロイメント、1つのイメージレシピ

本番環境は、同じコードベースの独立した2つのデプロイメントです。

- **roomake.top** — global のロケールスコープ、国際チェックアウト、独自のデータベースとメディアストレージ。
- **www.roomake.cn** — zh 専用のスコープ、中国大陸向けチェックアウト、完全に分離されたデータ。

実行時に共有するものは何もありません。片側の悪いリリースがもう片側へ触れることはできず、データのバグも越境できません。コストは、パイプラインを2本回すことです。そしてそのコストは払う価値があります——リージョン分離は、コンプライアンスの物語であると同時に、爆発半径の物語でもあるからです。

## ビルド時フラグは契約である

デプロイメント間で異なるものは、すべてビルド時フラグ（ロケールスコープ、インデックスのオン/オフ、公開 URL）であり、`next build` の間にバンドルへインライン化されます。これを安全に保つルールが3つあります。

1. **フラグを変えるなら、再起動ではなく再ビルド。** インライン化済みの定数に対して、実行時の環境変数変更は黙って何もしません——何も「出荷」していないのに出荷したつもりでいられる、古典的な方法です。
2. **危険なフラグは fail closed。** `NOINDEX` スイッチのデフォルトは*オン*です。環境ファイルの1行が欠けたリリースが生むのは隠されたサイトであって、うっかり公開されたサイトでは決してありません。
3. **環境変数のキーは許可リストを2回通る**——1回は Dockerfile の `ARG` 宣言で、もう1回は compose ファイルの build args で。両方のゲートを通れない変数は、そもそもビルドに入りません。設定が忍び込む第三の経路は存在しないのです。

リリースの儀式は、この順で: チェックリストと突き合わせて環境ファイルを `cat` → ビルド → デプロイ → 直ちに本番の `robots.txt`、サイトマップ、canonical URL を1本 `curl`。30秒の偏執性が、2つの古典的な災害（サイトがうっかり noindex された。サイトがうっかりプレビュービルドを晒した）を防いでくれます。

## キャッシュトポロジ

- **静的アセット**（JS chunk、フォント、画像）: CDN エッジで遠い未来までのキャッシュヘッダを付け、ファイル名は内容ハッシュ付きにします。永遠にキャッシュし、名前の再使用をしないことで無効化します。
- **HTML**: エッジで短い TTL。マーケティングページはめったに変わりませんが、変わったときの修正は、グローバルキャッシュの失効を待つのでなく、数分で見えるべきものです。緊急の訂正は明示的なキャッシュパージで通します。それは文書化され、リハーサル済みの行動であって、民間療法ではありません。
- **動的な面**（ツール、アカウントページ）: エッジでは決してキャッシュせず、セッション安全なヘッダはアプリ側で設定します。

フォントはビルド時にセルフホストします。そのため、フォントの配信が第三者の稼働状況に左右されることも、初回描画にクロスオリジンの DNS 往復を上乗せすることもありません。

## リファクタリングの前にゴールデンマスター

デプロイメントパイプラインで最も価値のある習慣は、記録の規律です。ページをレンダリングするコードに触れる**前**に、コアページのレンダリング HTML をロケールスコープごとにゴールデンマスターとして記録し、**後**には diff が空であることを要求します。「私の目には同じに見える」はリグレッションテストではありません。ベースラインは*旧*コードから記録しなければなりません。リファクタリングの後に記録するのは、自分のバグを基準として録画しているのと同じです。

## リリースチェックリスト（簡略版）

1. 環境ファイルを許可リストと突き合わせて監査（両方のゲート: Dockerfile の `ARG`、compose args）。
2. ゴールデンマスター diff がすべてグリーン（有効な全スコープ）。
3. インタラクティブなルートにバンドル予算チェック。
4. デプロイ → 本番スモーク: `robots.txt`（インデックス状態が正しいこと）、`/sitemap.xml`（ロケール行列が正しいこと）、ロケールごとに canonical URL を1本ずつ確認して、200 を返し、末尾スラッシュの 308 がないこと。
5. クリーンなセッションから、アナリティクス/ハートビートを検証。
6. ルートが変わったらサイトマップを再送信。ユーザーが待っている修正のリリースなら、キャッシュをパージ。

## ロールバックの階段、烈度が上がる順に

1. **機能レベルのフラグ** — 機能を切って、リリースは残す。
2. **スコープ/環境フラグ + 再ビルド** — デプロイメントを前の挙動のセットへ戻す（例: ロケールを1つ外す）。
3. **プロキシレベルの 301 マップ** — 検索エンジンがインデックスした可能性のあるルートを削除する前に、リダイレクトを設置します。削除はリダイレクトの後であって、その前では決してありません。
4. **前のイメージ** — 最後に正常だったことがわかっているビルドを再デプロイします。データは独立しているので、イメージは差し替え可能です。

この階段の背後にある常設ルール: *ロールバックは、インデックス済み URL を 404 に変えてはならない。* リダイレクトは資産を吸収します。404 は、それを誰にも渡さずに捨てます。

## オブザーバビリティとバックアップ

- プロダクトの指標にはセルフホストのクッキーレス・アナリティクス。デバッグ用にサーバーログはマシンの外へ送出。`/` とツールのルートにはアップタイム監視。
- バックアップ: データベースファイルとユーザーメディアを毎日、配信しているマシンでは*ない*ストレージへ。そしてリストアを検証済み——検証されていないバックアップは、願望であってバックアップではありません。

## ゼロから始めるチームに伝えたいこと

1. メタデータ生成器と、サイトマップ/hreflang のアサーションは、ローンチ週の**前**に組み込んでください。後から SEO の配管を付け足すのは苦役です。
2. noindex のキルスイッチは初日から存在させ、デフォルトは安全側に設定してください。
3. エンジン/プロバイダーは、薄い内部インターフェースの背後に置いてください。AI ベンダーは誰もが稼働率を約束しますが、価格の安定を約束する者は一人もいません。
4. 小規模では、隔離された2つのリージョンデプロイメントが、賢い1つのマルチテナントシステムに勝ります。
5. 構築の過程を書き残してください。未来のあなたも、チームメイトも、それだけで速く出荷できるようになります。
