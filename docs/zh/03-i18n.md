# 03 · i18n 架构 —— 六个语言、一套代码、不对爬虫说谎

## 一套代码，按部署定语言范围

同一套构建支持四种 **locale scope**，由一个环境变量在构建期定死：

| Scope | 生成的路由 | 用于 |
|---|---|---|
| `en` | 仅英文 | 内部/预览构建 |
| `zh` | 仅简体中文 | roomake.cn |
| `both` | EN + `/zh` | 过渡期 |
| `global` | EN（根路径）+ `/ja` `/de` `/fr` `/ko` | roomake.top |

让它安全成立的机制：`[locale]` 段的 `generateStaticParams` 返回当前 scope 的语言列表——zh 单语构建返回空列表——配合 `dynamicParams = false`，列表之外的语言请求在**构建期就是硬 404**，而不是渲染出一个软 404 页。爬虫永远发现不了「翻译了一半」的语言，因为没构建的语言在产物里根本不存在。

URL 结构是最朴素的了：英文在根路径，其他语言挂 `/{locale}/`。不用语言子域，不用查询参数，公共页不做 Cookie 语言协商（SEO 一节讲为什么）。

## 多根布局，保住 `<html lang>` 的真实

Next.js 16 支持路由组下的多根布局，这是让 `<html lang>` 保持诚实的最干净做法：`(main)` 组装英文树，`(i18n)/[locale]` 组装本地化树，每个根布局各自写自己的 `lang`。不用客户端补写属性——爬虫和翻译工具读到的服务端 HTML 就是正确的。

两个让我们花过时间的 Next 16 细节：

- **`params` 是 Promise。** 动态布局/页面必须是 `async` 组件并 `await params`。TypeScript 构建能逮住它——前提是你没绕过类型检查。
- **真正的全局 404 要开 `experimental.globalNotFound`。** 多根布局下，未匹配的顶层 URL 不走常规 `not-found.tsx`。这个全局 404 文件必须自带完整 `<html>`/`<body>`，并且**感知 scope**——zh 单语部署的 404 页必须与既往逐字节一致。共享构建配置的影响是全局的，每个 scope 都要测。

## 不用框架的字典方案

翻译就是带类型的 TypeScript 字典，按功能域组织，**语法需要处用函数字段**——德语复数、日语韩语量词都表达成函数，不是字符串插值。英文字典是形状事实源，其他语言必须填满同一类型。

让重构安全的纪律是**黄金母版 diff**：英文字符串抽取进字典系统时，验收标准是核心页渲染 HTML **逐字节不变**。「没有视觉回归」是观点，空 diff 才是事实。

## 什么翻译，什么不翻译

- **品牌词汇在所有语言保留英文**：风格名（Cream、Wabi Sabi……）、档位名、产品名。诗意副注翻译，专有名词不翻。
- **法务页以英文为权威版本**，本地语言只给指引行——除非法律要求真实的本地化披露（见下）。
- **其余全部本地化**，包括图片 `alt` 文本——室内设计是 Google 图片搜索的重度类目，alt 就是它的正门。

## 各语言踩过的坑

- **日语**：クレジット（credit）与クレジットカード（信用卡）同形——首次出现必须消歧。加 `line-break: strict` 处理标点禁则。音译成片假名的风格名只允许出现在文章里，不许进 UI。
- **韩语**：需要自己的衬线字体（见下）与原生量词；机翻的营销韩语一眼假，母语审校没有商量余地。
- **德语**：文本膨胀约 30%，固定宽度布局会破——长复合词（`Renovierungsvorschau` 这类）要在上线**前**在窄屏下测。
- **法语**：引号用 « »，不用直引号，写进字典编写规范。
- **日期**：一律 `Intl.DateTimeFormat(locale)`，禁止手写美式格式。
- **数字/货币**：各语言统一美元——定价品牌决策，贯彻到底。

## 字体：衬线身份与 CJK 现实

身份字体（Fraunces、Newsreader）经 `next/font` 构建期自托管。日语韩语在**匹配的 `html[lang]` 之下**经 CSS 变量注入 Noto Serif JP/KR——其他语言的页面永远不会下载 CJK 字形。

一个反直觉细节：Next 16 里日韩字体类型**不包含** `japanese`/`korean` subsets——CJK 字形切片由 `unicode-range` 自动完成。传 `subsets` 反而是类型错误；`preload: false` 且不传 subsets 才是正确写法。相信机制，不要相信「什么都配一遍」的直觉。

## 法务本地化，按类目处理

产品本地化会带来本地化法务义务。我们处理的类目：

- **日本**：真实的特定商取引法に基づく表記（销售主体名、責任者、地址、电话、邮箱、支付方式、服务提供时期、退款政策）——消费者厅对海外经营者的指引对必填字段写得明明白白。
- **德国**：Impressum 级别的运营者身份标识（DDG §5）。
- **法国**：LCEN 的出版负责人标识。
- **隐私附录**：日本的 APPI 跨境传输条款、韩国的 PIPA 告知条款、欧盟的 GDPR 要素（法律依据、撤回同意、跨境传输声明）——与「支付数据由 merchant of record 处理」的服务形态成比例。
- **不翻译、但处处链接**：权威英文版条款/隐私/退款页，挂在每个语言的页脚。

## 回滚：永远不让已收录 URL 变 404

用错误的顺序下线一个语言，会把那些 URL 积累的搜索权重直接蒸发。顺序是铁律：

1. 先在代理层架好退役语言到替代页（通常是英文页）的 301 重定向；
2. 然后才摘路由、重建。

任何结构改动同理：重定向在前，删除在后。GSC 会安静地吸收 301；对 404 它会叫。
